# 企业定制与官方主线同步

状态：implemented
类型：process
Owner：web/src/views/HomeView.vue

## 问题

企业部署在官方 Yuxi 基础上维护品牌页面、部署参数、数据库兼容迁移、Skill 权限兼容和文件上传限制。官方仓库重写了 `main` 历史，无法通过普通合并可靠地区分企业定制与历史重写产生的伪冲突。本次同步需要以官方最新代码为运行时底座，同时保留企业部署依赖的定制行为，并让企业 GitHub `main` 可以从现有历史非强制快进到融合结果。

## 提案

以当前官方 `upstream/main` 为内容基线，按旧官方基线到本地企业提交的内容差异迁移企业定制。品牌页面和静态资源、部署参数、已有数据库兼容迁移、Skill 权限兼容以及 500 MB 上传限制由对应源码和配置继续拥有；官方功能、安全修复、依赖和架构演进保持为默认结果。完成内容验证后，通过只连接历史而不改变工作树的合并提交接回既有企业主线，使远端 `main` 可以非强制更新。

## 替代方案

- 直接合并两条 `main`：官方强制重写后的共同祖先过早，会产生大量与真实业务无关的冲突，无法形成可信审查。
- 先更新 GitHub Fork 再拉取本地：会让远端官方内容暂时覆盖企业定制，并把真实冲突留到本地二次处理，增加丢失定制的风险。
- 以企业分支为底座逐个引入官方提交：官方重写后的提交数量过多，容易遗漏安全和架构更新，也无法稳定对应新的官方历史。

## 风险

- 官方架构演进可能使旧企业兼容补丁失效，迁移时必须按当前语义 Owner 判断，而不是机械保留每个旧测试改动。
- 阿里云、上海交大和南京大学的 PyTorch 镜像尚未提供官方当前要求的 `torchvision 0.28.0`；普通 Python 包继续使用清华镜像，PyTorch 暂时保留官方 CPU 源以保证依赖可解。
- 数据库迁移和 Compose 定制需要真实容器与 PostgreSQL 验证，单元测试不能替代运行时证据。
- UI 定制需要在新版路由、主题和响应式布局中重新验证，构建成功不能替代真实页面检查。
- 历史连接提交只能在融合工作树已完整验证后创建，否则会隐藏内容遗漏。
- 全量后端 unit 运行到约 76% 时，官方现有 `test_process_subagent_run_restores_runtime_context` 会无限等待；该用例单独运行结果相同，相关改动范围已由上述定向测试覆盖。
